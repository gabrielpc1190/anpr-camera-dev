# Diseño: Soporte multilenguaje (español + inglés) para la UI

**Fecha**: 2026-06-05
**Autor**: gabriel + Claude (brainstorming)
**Estado**: Aprobado, listo para `writing-plans`

---

## 1. Problema y contexto

Hoy la UI de `anpr-web` (templates HTML + strings dinámicas en JS + mensajes del backend Flask) está hardcodeada en una mezcla de español/inglés. Los 4 viewers actuales son cuentas para clientes externos que podrían preferir un idioma específico. No existe ningún mecanismo de internacionalización.

El requerimiento del usuario: *"Seguimos con el multilenguaje, español e inglés."*

## 2. Objetivos y fuera de alcance

### En alcance

1. Toggle ES/EN visible en el header del dashboard y de la página de login.
2. La selección se persiste en una cookie del navegador (sin cambios a la DB).
3. Default `es` cuando no hay cookie.
4. Cobertura completa de strings visibles al usuario:
   - `templates/login.html`, `templates/index.html`, `templates/admin.html` (HTML + JS inline).
   - Mensajes flash de Flask-Login y `jsonify({'error': ...})`/`'message': ...` del backend `anpr_web.py`.
5. Arquitectura simple: dos archivos JSON (`es.json`, `en.json`) como única fuente de verdad, leídos por anpr-web al startup.
6. Helpers consistentes: `t(key)` en Python (template + backend) y `t(key)` en JS.
7. Documentar deployment + rollback como apéndice operacional.

### Fuera de alcance

- Idiomas adicionales (solo ES y EN; el diseño deja la puerta abierta para más en el futuro pero no se implementan).
- Pluralización gramatical (`1 evento` vs `5 eventos`). Strings con números usan formato neutro.
- Localización de formato de fecha/hora/número. Timestamps se mantienen en formato ISO universal.
- RTL (right-to-left): ambos idiomas seleccionados son LTR.
- Traducción de:
  - Nombres propios en DB: `cameras.friendly_name`, `camera_groups.name`, `user.username`.
  - Placas de vehículos y datos crudos del payload.
  - Logs del servidor (`logger.info`, `logger.error`) — son para ops, no para usuarios.
- Sincronización con otros dispositivos del mismo usuario (la preferencia es por navegador, no por cuenta).

## 3. Decisiones arquitectónicas clave

**Cookie como mecanismo de selección.** El idioma vive en una cookie `lang=es|en` con `max_age=1 año, SameSite=Lax`. No requiere cambios al schema de DB ni al modelo `User`. Cada navegador del usuario tiene su propia preferencia.

**JSON dicts como fuente de verdad.** Dos archivos `app/translations/es.json` y `app/translations/en.json` con la misma estructura plana key→value. anpr-web los carga al startup en un dict Python `TRANSLATIONS`. Para 2 idiomas y ~160 strings totales, esta arquitectura es significativamente más simple que flask-babel/gettext y da exactamente la misma UX.

**Convención de keys plana en snake_case.** Formato `<area>.<element>[.<modifier>]`. Ejemplo: `header.logout`, `table.col.plate`, `status.trust_car`. Permite búsquedas rápidas (`grep "table\." es.json`) y deja la estructura plana fácil de mantener.

**Mismo `t(key)` en 3 contextos.** Python backend (en handlers), Jinja templates (via `context_processor` que inyecta `t` automáticamente), y JS (`window.__i18n` inyectado en el `<head>`). Las tres formas usan el mismo archivo JSON y la misma key.

**Fallback visible para gaps.** Si una key no existe en el idioma actual, `t(key)` devuelve la propia key como string literal (ej. `"table.col.plate"`). Es feo en pantalla, pero **deliberadamente visible** para detectar gaps rápido en QA.

**Fail-fast al startup.** Si un archivo JSON no se puede leer o no parsea, anpr-web crashea al arrancar. No queremos producción corriendo con i18n a medias.

**Cambio de idioma vía endpoint dedicado, no AJAX.** `GET /set-lang/<lang>?next=<url>` setea la cookie y redirecta. Botones del header son simples `<a href>`. Cero JS para el toggle.

## 4. Arquitectura

### Estructura de archivos

```
app/
├── anpr_web.py              # Modificado: load TRANSLATIONS, helpers, endpoint, context_processor
├── translations/            # Nueva carpeta
│   ├── es.json              # ~160 keys
│   └── en.json              # ~160 keys
└── templates/
    ├── login.html           # Modificado: t() + toggle ES/EN
    ├── index.html           # Modificado: t() + toggle ES/EN + window.__i18n
    └── admin.html           # Modificado: t() + toggle ES/EN + window.__i18n
```

### Flujo de request

1. Usuario abre el dashboard.
2. anpr-web lee `request.cookies.get('lang', 'es')` y valida contra `SUPPORTED_LANGS = ('es', 'en')`.
3. El `context_processor` inyecta en cada template: `t` (función), `current_lang` (string), `translations_json` (dict serializado del idioma activo, para JS).
4. Jinja renderiza con `{{ t('header.title') }}` en cada string traducible.
5. El template incluye `<script>window.__i18n = {{ translations_json | safe }};</script>` en el `<head>`.
6. JS dinámico usa `function t(key) { return window.__i18n[key] || key; }`.

### Backend `anpr_web.py` — cambios

**Imports + carga (top-level)**:
```python
import json
TRANSLATIONS = {}
for lang in ('es', 'en'):
    with open(f'/app/app/translations/{lang}.json', encoding='utf-8') as f:
        TRANSLATIONS[lang] = json.load(f)
SUPPORTED_LANGS = ('es', 'en')
DEFAULT_LANG = 'es'
```

**Helpers + context processor**:
```python
def get_lang():
    lang = request.cookies.get('lang', DEFAULT_LANG)
    return lang if lang in SUPPORTED_LANGS else DEFAULT_LANG

def t(key):
    return TRANSLATIONS[get_lang()].get(key, key)

@app.context_processor
def inject_i18n():
    lang = get_lang()
    return {
        't': t,
        'current_lang': lang,
        'translations_json': json.dumps(TRANSLATIONS[lang]),
    }
```

**Endpoint de cambio**:
```python
@app.route('/set-lang/<lang>')
def set_lang(lang):
    if lang not in SUPPORTED_LANGS:
        abort(400)
    next_url = request.args.get('next', request.referrer or url_for('index'))
    if urlparse(next_url).netloc != '':
        next_url = url_for('index')
    resp = make_response(redirect(next_url))
    resp.set_cookie('lang', lang, max_age=365*24*3600, samesite='Lax')
    return resp
```

**Refactor de strings hardcodeados**:
- `flash('Invalid username or password')` → `flash(t('login.invalid'))`.
- `jsonify({'error': 'Username and password are required'})` → `jsonify({'error': t('user.error.username_password_required')})`.
- Todos los strings del módulo de validación de password (`is_password_strong`), etc.

### Toggle UI (HTML)

En el header de `index.html` y `admin.html`:
```html
<div class="flex items-center space-x-1 ml-3">
  <a href="/set-lang/es?next={{ request.path }}"
     class="px-2 py-1 text-sm rounded {% if current_lang == 'es' %}bg-white text-blue-600 font-semibold{% else %}text-white hover:bg-blue-700{% endif %}">ES</a>
  <a href="/set-lang/en?next={{ request.path }}"
     class="px-2 py-1 text-sm rounded {% if current_lang == 'en' %}bg-white text-blue-600 font-semibold{% else %}text-white hover:bg-blue-700{% endif %}">EN</a>
</div>
```

En `login.html`, similar pero adaptado a la layout de login.

### Inyección JS

En `<head>` de cada template (después de cargar Tailwind):
```html
<script>window.__i18n = {{ translations_json | safe }};</script>
```

Helper JS (al inicio del script principal de cada template, o en un bloque compartido):
```js
function t(key) { return window.__i18n[key] || key; }
```

## 6. Edge cases cubiertos

| Caso | Comportamiento |
|---|---|
| Cookie con valor inválido (`lang=fr`) | `get_lang()` cae a `DEFAULT_LANG` (`es`). |
| Key faltante en el idioma actual | `t(key)` devuelve la propia key como string. Visible en UI para detectar gaps. |
| Login sin sesión | La cookie funciona igual. Sin cookie → default `es`. Toggle visible en login también. |
| Interpolación de variables | Strings con `{name}` en el JSON se invocan con `.format(name=value)` en Python o template literal/`.replace()` en JS. |
| Open redirect en `/set-lang/<lang>?next=...` | Validar que `urlparse(next).netloc == ''` (mismo patrón que el endpoint `/login` ya usa). |
| Archivo JSON corrupto al startup | Fail-fast: el servicio crashea con error claro. No se desploya código con i18n a medias. |
| Pluralización | No implementada; strings neutras del tipo `"{n} eventos"`. |
| RTL | Fuera de alcance. Ambos idiomas LTR. |

## 7. Plan de deployment + rollback

### Pre-deploy

Respaldo del código (no de DB, no se toca):

```bash
TS=$(date +%Y%m%d_%H%M%S)
sudo tar czf /root/anpr-camera-dev/backups/code_pre_i18n_${TS}.tar.gz \
  -C /root/anpr-camera-dev \
  app/anpr_web.py \
  app/templates/login.html \
  app/templates/index.html \
  app/templates/admin.html
```

### Deploy

`sudo docker-compose build anpr-web && sudo docker-compose up -d anpr-web`. ~2 min.

### Validación post-deploy

1. Page load sin cookie → UI en español.
2. Click EN → cookie `lang=en`, página recarga, todo en inglés.
3. Login con credenciales inválidas en ambos idiomas → flash message correcto.
4. Admin abre modal "Crear grupo" en ambos idiomas → labels traducidos.
5. Viewer entra al dashboard en ambos idiomas → headers, columnas, status badges, paginación traducidos.
6. JS dinámico: toast de "Nuevo evento" en idioma activo.
7. Devtools console: cero errores. Keys faltantes aparecen como literal (anotables para corregir).

### Rollback Nivel 1 (único nivel necesario)

```bash
TS=<el TS apuntado pre-deploy>
sudo mkdir -p /tmp/restore_i18n
sudo tar xzf /root/anpr-camera-dev/backups/code_pre_i18n_${TS}.tar.gz -C /tmp/restore_i18n/
sudo cp -r /tmp/restore_i18n/app/* /root/anpr-camera-dev/app/
cd /root/anpr-camera-dev && sudo docker-compose build anpr-web
cd /root/anpr-camera-dev && sudo docker-compose up -d anpr-web
```

Como no se toca DB ni listener ni db-manager, **no hay niveles 2 o 3**.

## 8. Notas para implementación

- Carpeta `app/translations/` debe estar incluida en el `COPY` del Dockerfile de anpr-web. Verificar `anpr_web.Dockerfile` y, si solo copia `app/templates/`, agregar `COPY app/translations/ /app/app/translations/`.
- Para extraer las ~160 strings hardcodeadas, usar `grep -oE '>[A-Z][^<>{}]+<'` y similares sobre cada template. Listar todas, asignar key, agregar a ambos JSONs. Trabajo manual de ~1 hora la primera vez.
- Mantener orden alfabético dentro del JSON para minimizar diffs futuros.
- Validación de JSON al CI/local: `python -c "import json; json.load(open('app/translations/es.json'))"` y mismo para en.json. Si CI no existe, hacerlo manualmente antes de commit.
- Para detectar keys huérfanas (definidas en JSON pero no usadas en código): grep cada key contra `app/templates/` y `app/anpr_web.py`. Si una key no aparece en ningún archivo, removerla.
- Para detectar strings no traducidas (hardcoded que se quedaron sin pasar por `t()`): inspección manual de templates renderizados en ambos idiomas durante la validación. El fallback de "key visible" ayuda.

## 9. Decisiones tomadas durante el brainstorming

- **Mecanismo de selección**: cookie por navegador (opción B). No por usuario en DB (opción A) ni auto-detect (opción C).
- **Default**: español.
- **Toggle**: visible en header del dashboard y login (no escondido en menú de settings).
- **Tooling**: JSON dicts custom, no flask-babel. Justificado por el tamaño pequeño (2 idiomas, ~160 strings) y simplicidad operacional.
- **Naming**: keys planas en snake_case con prefijo de área. Sin namespaces anidados.
- **Fallback de keys faltantes**: visible (key como texto) en vez de string vacío o crash, para detectar gaps en QA.
- **Pluralización**: explícitamente fuera de alcance. Strings neutras.
- **Localización de fechas**: fuera de alcance. Timestamps ISO universales.
- **Cambio de idioma**: endpoint dedicado `/set-lang/<lang>` que setea cookie + redirect. Sin AJAX.
- **Fail-fast al startup**: archivo JSON ilegible → servicio no arranca.
- **Rollback**: solo Nivel 1 necesario (feature 100% aditiva, no toca DB).
